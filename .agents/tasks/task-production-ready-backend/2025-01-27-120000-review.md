# Production hardening for CryptoMine Express backend

The change layers production concerns onto a single-file Express/SQLite backend: environment-based configuration via dotenv, security headers via helmet, two-tier rate limiting, input validation for phone and comment fields, a health check endpoint, a global error handler, and graceful shutdown signal handlers. A `.env.example` and Heroku Procfile round out the deployment story.

**Watch for:** The graceful shutdown calls `process.exit(0)` without closing the HTTP server, so in-flight requests are dropped rather than drained (confirmed). The rate limiter uses the default in-memory store, which resets on every restart and doesn't work across multiple processes (confirmed). The JWT fallback secret ships in plain text in source, meaning the app runs with a known secret if the env var is accidentally missing in production (confirmed).

## High-level view

The JWT secret is extracted to an env var with a dev fallback and a console warning when absent. However, the fallback is a known string in source control, so a misconfigured production deploy silently operates with a guessable secret — a fail-open posture.

Rate limiting applies a 100-request general cap and a 10-request auth cap per 15-minute window, but both use express-rate-limit's default `MemoryStore`. This works for a single-process deployment but resets on every restart, which could be exploited by forcing a crash or deploying frequently.

Input validation covers phone regex, comment trim/length cap, and account trim. The login route is not validated the same way as register (no regex check on phone), creating an asymmetry that could matter in future refactors.

Graceful shutdown closes the database but does not call `server.close()` on the HTTP listener, meaning in-flight requests get TCP-reset rather than completing. This is the most actionable gap in the change.

1. **Graceful shutdown drops in-flight requests** — The SIGTERM/SIGINT handlers call `db.close(); process.exit(0)` without first calling `server.close()` to stop accepting new connections and drain existing ones. 3. **Rate limiter resets on restart (memory store)** — The default in-memory store loses all counters on process restart. 4. **Login route skips phone regex validation** — `/api/auth/register` validates phone with `/^\d{9,15}$/` but `/api/auth/login` does not. Low severity since parameterized queries prevent injection, but inconsistent validation hides future risks. Add the same regex check to login. (confirmed)
5. **No request body size limit** — `express.json()` is called without a `limit` option. Default in Express 5 is 100KB, but this app's largest legitimate payload is a 500-char comment. Consider `express.json({ limit: '10kb' })` to reduce memory allocation from oversized requests. (likely)

## Shutdown lifecycle gap

The signal handlers close the SQLite database and immediately exit:

```js
process.on('SIGTERM', () => {
  console.log('SIGTERM received. Shutting down gracefully...');
  db.close();
  process.exit(0);
});
```

The return value of `app.listen(PORT, ...)` is never captured, so there's no reference to the HTTP server to call `server.close()` on. In a Heroku-style deploy, the platform sends SIGTERM and gives the process 30 seconds to drain. Without `server.close()`, in-flight requests get TCP-reset mid-response. The fix:

```js
const server = app.listen(PORT, () => { ... });

process.on('SIGTERM', () => {
  server.close(() => {
    db.close();
    process.exit(0);
  });
});
```

## JWT secret fail-open behavior

The warning log when `JWT_SECRET` is unset is a good developer signal, but in production the consequence is silent operation with a known secret — any actor who reads this source can forge tokens. The safer pattern:

```js
if (!process.env.JWT_SECRET && process.env.NODE_ENV === 'production') {
  console.error('FATAL: JWT_SECRET must be set in production');
  process.exit(1);
}
```

This converts fail-open to fail-closed without affecting local development.

## Rate limiting scope and store

The general limiter at `/api/` and the auth limiter at `/api/auth/` stack correctly — auth routes hit both limiters, so they're effectively capped at 10 requests. The `/health` endpoint bypasses rate limiting (mounted outside `/api/`), which is correct for load balancer probes.

The memory store limitation means that if the Procfile ever runs multiple workers via `cluster`, the limits become per-worker and effectively multiplied. Worth a code comment documenting the single-process assumption.

## Input validation asymmetry

Registration validates phone numbers with `/^\d{9,15}$/`, rejecting letters and special characters. Login passes the raw `phone` directly into the parameterized query without the same check. The parameterized query prevents SQL injection today, but the inconsistency means a future refactor that adds phone-based rate-key derivation or logging could pass unsanitized input into those paths.

The comment length cap (500 chars via `substring(0, 500)`) silently truncates without informing the user. Not a security issue, but a potential source of user confusion.
