# SQLite-to-PostgreSQL migration for Neon/Render deployment

The backend database layer moves from synchronous better-sqlite3 to async node-postgres (`pg`), rewiring every route handler and SQL statement in server/index.js. The frontend API layer gains a configurable base URL via `VITE_API_URL`, and a render.yaml provides one-click Render deployment for both services. All SQL syntax is converted (SERIAL, $-params, NOW(), CURRENT_DATE, RETURNING), transactions use the client-checkout pattern, and startup is restructured into an async `initDb()` that gates `app.listen`.

**Watch for:** Race conditions in multi-step financial operations that don't use a transaction (confirmed). SSL configuration that will break in local development (confirmed). Product seeding conflicts with SERIAL sequence via explicit ID insertion (likely). No migration path for existing data (confirmed — design choice, but worth noting).

## High-level view

Several multi-step financial operations (deposit, withdraw, purchase, blog post with reward) perform multiple writes outside a transaction, creating windows where a crash leaves the database in an inconsistent state. Only `collect-earnings` correctly uses a client-checkout transaction. The withdraw route also has a TOCTOU race on the balance check under concurrent requests.

The pool is constructed with `ssl: { rejectUnauthorized: false }` unconditionally, which means local development against a plain-TCP Postgres will fail to connect. This is a DX friction that should be gated on `NODE_ENV`.

Product seeding inserts explicit IDs (1–8) into a SERIAL column without resetting the sequence, so the next auto-generated ID will collide with existing rows on the first dynamically-created product insert.

<details>
<summary>Issues (5)</summary>

1. **Financial operations lack transactions** — Deposit, withdraw, purchase, and blog-post-with-reward each perform multiple writes (balance update + transaction record) without a BEGIN/COMMIT block. A crash between writes leaves balance and ledger out of sync. Wrap each in a client-checkout transaction.
2. **SSL forced in all environments** — `ssl: { rejectUnauthorized: false }` is hardcoded. Local Postgres without TLS will refuse to connect. Gate it on `NODE_ENV === 'production'` or parse `DATABASE_URL` for sslmode.
3. **SERIAL sequence not synced after explicit ID insert** — Seeding products with explicit IDs (1–8) does not call `setval()` on the sequence. The next `INSERT INTO products` without an ID will attempt id=1 and fail with a unique violation.
4. **Register referral creation is non-atomic** — The registration flow inserts a user and then a referral record as two independent `pool.query` calls. If the server crashes between them, the referral is lost. Use a transaction.
5. **`initDb()` failure leaves pool open** — If `initDb()` throws, the `.catch()` calls `process.exit(1)` but doesn't call `pool.end()` first, potentially leaving connections dangling briefly on the server side.

## Transaction gaps in financial routes

The `collect-earnings` route correctly acquires a client, wraps all mutations in BEGIN/COMMIT, and releases on error. The other financial routes do not. In `/api/deposit`:

```js
await pool.query('UPDATE users SET balance = balance + $1 ...', [amount, req.userId]);
await pool.query('INSERT INTO transactions ...', [genId(), req.userId, ...]);
```

If the process crashes or the connection drops between these two statements, the user's balance is incremented but no transaction record exists. The same pattern repeats in `/api/withdraw`, `/api/purchase`, and `/api/blog` (POST). Each of these should use a client-checkout transaction identical to the one already implemented in `collect-earnings`.

The withdraw route has an additional subtlety: it reads the user's balance, then decrements it in a separate query. Under concurrent requests from the same user, two withdrawals could both pass the balance check and overdraw the account. A `WHERE balance >= $1` guard on the UPDATE, checked via `rowCount`, would close this race.

## SSL configuration rigidity

```js
const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  ssl: { rejectUnauthorized: false }
});
```

Neon requires TLS, so this works in production. A developer running local Postgres without TLS will get a connection error. A common fix:

```js
ssl: process.env.NODE_ENV === 'production' ? { rejectUnauthorized: false } : false
```

`rejectUnauthorized: false` disables certificate verification, making the connection vulnerable to MITM. For Neon specifically this is the documented approach, but if the deployment target changes, this should be revisited.

## SERIAL sequence desync on product seeding

The products table uses `id SERIAL PRIMARY KEY`, but seeding inserts explicit IDs:

```js
await client.query('INSERT INTO products (id, name, ...) VALUES ($1, ...)', [1, 'Miner S1', ...]);
```

PostgreSQL's sequence backing a SERIAL column is not automatically advanced when you insert explicit values. After seeding 8 rows, `nextval('products_id_seq')` still returns 1. Any future INSERT that relies on the sequence will hit a duplicate-key error. Fix: after seeding, run `SELECT setval('products_id_seq', (SELECT MAX(id) FROM products))`.

## Registration atomicity

User creation and referral record insertion are two independent `pool.query` calls not wrapped in a transaction. If the process dies after creating the user but before inserting the referral, the referrer never sees the new member in their team. The blast radius is small (low-frequency operation), but the fix — a three-statement transaction — is trivial.

## Startup failure cleanup

```js
initDb().then(() => { ... }).catch((err) => {
  console.error('Failed to initialize database:', err);
  process.exit(1);
});
```

`pool.end()` is not called before exit. Node's process termination closes TCP sockets, so this is cosmetic rather than a data-safety issue, but it can leave "idle in transaction" connections visible on the Neon dashboard until the server-side timeout fires.
